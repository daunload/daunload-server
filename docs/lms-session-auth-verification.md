# LMS 비밀번호 미수집 및 세션 재발급 검증

- 작성일: 2026-11-06
- 결과 기준 시각: 2026-11-06 18:44 KST
- 상태: 초기 검증 완료, 장기 관찰 결과 미확정, 비밀번호 미저장 구조 구현(9절)
- 범위: 공개 로그인 경로 분석, 현재 코드 분석, 사용자가 허용한 본인 계정의 인증 테스트

이 문서는 기준 시각까지 확인된 결과를 기록한다. 이후 측정 결과는 자동으로 반영되지 않는다. 학번, 비밀번호, 쿠키 및 토큰 원문은 포함하지 않는다.

## 1. 요구사항과 현재 결론

요구사항은 다음과 같다.

1. 자동 수강 기능을 유지한다.
2. 운영자가 사용자의 학교 비밀번호 원문을 알아낼 수 없는 구조를 지향한다.
3. 이를 보장할 수 없다면 학교 비밀번호를 서비스에서 수집하지 않는다.

**유효한 SSO 토큰으로 학교 비밀번호를 다시 전송하지 않고 학습 인증을 재발급받는 경로를 실제로 확인했다.** 이를 바탕으로 학교 비밀번호를 저장하지 않는 자동 수강 구조를 설계할 수 있다.

다만 SSO 토큰 자체의 최대 수명과 갱신 가능성은 아직 확인하지 못했다. 무기한 자동 수강이나 사용자 개입 없는 영구 재인증을 보장할 수 없다. 브라우저에서 인증 정보를 연동하는 전체 흐름과 실제 자동 수강 완료도 이번 검증 범위에 포함되지 않았다.

## 2. 현재 서비스의 비밀번호 처리

현재 코드는 학교 비밀번호를 다음 두 형태로 저장한다.

| 항목 | 용도 | 원문 복원 |
| --- | --- | --- |
| `User.password_hash` | 서비스 로그인 검증 | 해시 자체를 복호화하는 방식은 아님 |
| `LmsCredential.password_enc` | 학교 자동 재로그인 | 서버의 Fernet 키로 복호화 가능 |

DB의 비밀번호 암호문과 서버 암호화 키에 모두 접근할 수 있는 운영자는 원문을 복원할 수 있다. 현재 LMS 접근 코드는 저장된 비밀번호를 실제로 복호화해 재로그인에 사용한다.

KMS는 키 관리, 복호화 권한 분리, 감사 기록을 개선할 수 있다. 하지만 서버 코드·배포·실행 환경을 통제하는 운영자로부터 입력 비밀번호나 복호화된 원문을 완전히 숨기는 수단은 아니다. 따라서 KMS 적용만으로 비밀번호 미수집 또는 운영자의 원문 접근 불가능을 주장해서는 안 된다.

현재 운영 코드의 비밀번호 저장 방식은 변경하지 않았다. 미수집 전환 시 기존 학교 비밀번호 암호문과 해시, 백업에 남은 데이터의 처리도 별도로 계획해야 한다.

## 3. 학교 인증 구조

공개 페이지에서 확인한 로그인 진입 경로는 다음과 같다.

```text
https://lms.ssu.ac.kr/
  → /login?type=xn-sso-dir-sso
  → /xn-sso/gw.php
  → /xn-sso/login.php
  → https://smartid.ssu.ac.kr/Symtra_sso/smln.asp
  → 학교 공식 로그인 폼에서 smln_pcs.asp로 제출
  → https://lms.ssu.ac.kr/xn-sso/gw-cb.php
```

현재 인증 구현과 실제 계정 테스트에서 확인한 학습 인증 연결은 다음과 같다.

```text
학교 SSO
  → LMS 게이트웨이
  → Canvas 로그인 연결
  → Canvas 쿠키 + LearningX API 토큰
  → 학습 기능 접근
```

| 구성 | 역할 |
| --- | --- |
| `smartid.ssu.ac.kr` | 학교 통합 로그인 |
| `lms.ssu.ac.kr` | LMS 포털 및 SSO 연결 |
| `lms.ssu.ac.kr/xn-sso/` | SSO와 학습 시스템 사이의 게이트웨이 |
| `canvas.ssu.ac.kr` | Canvas 및 LearningX API |
| `commons.ssu.ac.kr` | 강의 콘텐츠 제공 |

학교 SSO 인증과 학습 시스템 인증은 구분된다. 포털 쿠키의 유효성만으로 학습 기능 전체의 인증 상태를 판단해서는 안 된다.

공개 응답에서 관찰한 `coursecatalog_session` 및 SSO 세션 쿠키 일부는 명시적인 만료 날짜가 없었다. 이는 서버 측 무기한 유효성을 의미하지 않는다. 로그인 시도 식별용 쿠키, CSRF 쿠키, 로그인 화면의 ‘아이디 저장’ 기능 역시 장기 인증 유지의 증거가 아니다.

## 4. 실제 검증 결과

| 검사 | 결과 | 해석 범위 |
| --- | --- | --- |
| 학교 최초 로그인 | 성공 | 제공받은 계정으로 인증 가능 |
| Canvas 쿠키 인증 | 성공 | API 토큰과 분리해서 검사 |
| LearningX 토큰 인증 | 성공 | Canvas 쿠키와 분리해서 검사 |
| 비밀번호 재로그인 없는 학습 인증 유지 | 90분 후에도 성공 | 30분 간격 요청이 있는 상태 |
| Canvas 쿠키를 제외한 접근 | HTTP 401 | 해당 테스트 클라이언트에 학습 쿠키 인증이 없음 |
| 기존 SSO 토큰으로 게이트웨이 연결 | 성공 | 학교 비밀번호를 다시 제출하지 않음 |
| API 토큰 재발급 | 기존과 다른 값 발급 및 인증 성공 | HTTP 200 및 예상 JSON 구조 확인 |
| Canvas 쿠키 재발급 | 인증 성공 | HTTP 200 및 예상 JSON 구조 확인 |
| 같은 SSO 토큰의 반복 사용 | 최초·1분·2분 후 모두 성공 | 매번 기존 Canvas 쿠키를 제외하고 학습 인증 재발급 |
| SSO 토큰 값 변경 | 관찰되지 않음 | 토큰 수명 연장 여부는 판단 불가 |

일반 로그인 진입 URL은 기존 쿠키가 있어도 학교 비밀번호 입력 화면으로 이동했다. 반면 발급된 SSO 토큰을 학교 게이트웨이에 전달하는 정상 연결 경로에서는 학습 인증 재발급이 성공했다.

학교는 Canvas 연결 과정에서 별도 로그인 자격정보를 전달한다. 테스트 계정에서 이 값이 제공된 학교 비밀번호와 다른지 메모리에서 비교했고, **서로 다른 값임을 확인했다.** 이는 해당 계정·검사 시점의 결과이며 모든 계정이나 향후 동작에 대한 보장은 아니다. 해당 자격정보 역시 민감한 인증 정보로 취급해야 한다.

Canvas API 응답에는 `while(1);` 접두사가 붙는 경우가 있었다. 초기 측정 도구는 이 응답을 판독하지 못했으나, 접두사를 처리하도록 수정한 뒤 정상 인증을 확인했다. 초기 판독 실패를 세션 만료로 계산하지 않았다.

## 5. 실험 방법과 한계

### 학습 인증 유지 관찰

- 최초 로그인 이후 비밀번호 자동 재로그인을 사용하지 않는다.
- 쿠키 인증 클라이언트와 Bearer 토큰 인증 클라이언트를 분리한다.
- 쿠키 인증에서는 응답으로 갱신된 쿠키를 메모리에서 유지한다.
- Bearer 인증에서는 응답 쿠키를 다음 검사에 사용하지 않는다.
- HTTP 상태뿐 아니라 예상 JSON 응답 구조도 검사한다.
- 요청은 읽기 전용이며 강의 재생이나 출석 기록 변경을 수행하지 않는다.

### SSO 재발급 관찰

- 최초 로그인으로 확보한 SSO 정보만 재발급 검사에 사용한다.
- 매회 Canvas 및 LMS 포털 쿠키를 제외하고, 학교 SSO 및 공통 도메인 쿠키로 새 클라이언트를 구성한다.
- 기존 SSO 토큰으로 학교 게이트웨이와 정상 Canvas 연결 절차를 수행한다.
- 발급된 쿠키와 API 토큰을 각각 검사한다.
- SSO 토큰이 변경되는지 비교하되 원문은 출력·저장하지 않는다.
- 갱신된 SSO 쿠키가 있으면 다음 관찰에 반영한다.
- 인증 이상이나 네트워크·응답 오류가 발생하면 관찰을 중단한다. 모든 중단을 ‘세션 만료’로 단정하지 않는다.

### 결과 해석 시 주의점

1. Canvas 쿠키를 클라이언트에서 제외한 실험은 학교 서버가 세션을 실제로 만료·폐기한 상태와 다르다.
2. 쿠키 값 변경이나 새 학습 토큰 발급만으로 SSO 수명이 연장됐다고 판단할 수 없다.
3. 같은 계정으로 추가 로그인과 다른 관찰이 진행됐으므로 엄격하게 격리된 미사용/활동 비교 실험은 아니다.
4. 같은 세션을 복제한 두 클라이언트는 한쪽의 활동이 다른 쪽의 유효성에 영향을 줄 수 있다. 별도 로그인도 계정 단위 정책의 영향을 받을 수 있다.
5. 일정 기간 성공한 것은 그 관찰 기간의 성공만 증명한다. 무기한 유지의 증거가 아니다.
6. 브라우저에서 발급한 인증 정보를 다른 실행 환경으로 이전하는 흐름은 아직 검증하지 않았다.

## 7. 아직 필요한 검증

- SSO 토큰의 최대 수명 및 절대 만료 여부
- 정상 요청이 SSO 미사용 만료를 늦추는지
- SSO 토큰 자체를 비밀번호 없이 갱신할 수 있는지
- 학습 세션의 실제 서버 측 만료 후 SSO 복구 가능 여부
- 계정의 다른 로그인·로그아웃이 기존 토큰에 미치는 영향
- 사용자 브라우저에서 발급한 인증 정보의 서버 연동 가능 여부
- 비밀번호 미수집 흐름으로 실제 자동 수강까지 완료할 수 있는지

## 8. 제품 설계에 반영할 방향

```text
사용자가 학교 공식 페이지에서 직접 로그인
  → 필요한 인증 정보만 서비스에 연동
  → 서버에서 자동 수강
  → 학습 인증 실패 시 유효한 SSO로 재발급
  → SSO도 실패하면 작업 일시 중지 및 사용자 재연동
```

이 흐름은 현재 검증 결과에 기반한 설계 방향이다. 9절의 구현은 첫 단계(사용자가 학교 공식 페이지에서 직접 로그인)를 제외한 나머지를 반영했다.

학교 비밀번호를 받지 않아도 서버가 SSO·학습 세션을 보관하면 운영자가 그 권한으로 LMS에 접근할 가능성은 남는다. 따라서 ‘학교 비밀번호 미수집’과 ‘운영자의 LMS 접근 불가능’을 구분해야 한다. KMS와 권한 분리는 세션 보호에 활용할 수 있지만 후자를 보장하지는 않는다.

서비스 로그인은 학교 비밀번호와 분리해야 한다. 기존 학교 비밀번호 암호문·해시 삭제, 백업 처리, 세션 폐기 및 사용자 재연동 절차는 전환 작업에 포함해야 한다.

## 9. 구현 및 검증 산출물

### 비밀번호 미저장 전환 (2026-11-06)

사용자의 브라우저에서 서버로 인증 정보를 옮기는 흐름은 아직 검증하지 않았다(5절 6번). 그래서 로그인 폼은 그대로 학번과 비밀번호를 받되 **저장하지 않는** 방식으로 먼저 전환했다.

| 항목 | 이전 | 현재 |
| --- | --- | --- |
| 서비스 로그인 | `User.password_hash` 비교, 처음이거나 비밀번호가 바뀌었을 때만 학교 로그인 | 매번 학교 SSO 로그인으로 확인 |
| 학교 비밀번호 | `LmsCredential.password_enc`(Fernet) 보관 | 요청 처리 중 메모리에서만 사용, DB·로그에 저장하지 않음 |
| 학습 세션 만료 | 저장된 비밀번호로 재로그인 | 저장된 SSO 토큰으로 재발급(`auth.renew_from_sso`) |
| SSO 만료 | 해당 없음 | `SsoExpired` → `LmsCredential.status = "invalid"`, 세션 삭제, 다시 로그인 알림 |
| 기존 데이터 | — | 마이그레이션 `f5a6b7c8d9e0`에서 `password_hash`, `password_enc` 컬럼 삭제 |

이 구조에는 한계가 있다.

- 로그인 요청은 서비스 서버를 거쳐 학교로 전달된다. 따라서 서버가 비밀번호를 저장하지 않는다는 점은 기술적으로 강제되지 않으며, 운영 정책과 공개된 코드에 대한 **신뢰**에 기반한다.
- 서버는 SSO 토큰과 학습 세션을 보관하므로, 운영자가 그 권한으로 LMS에 접근할 가능성은 남는다(8절).
- 학습 세션 재발급이 실패한 원인이 학교 서버 오류나 네트워크 오류(5xx, 연결 실패)이면 일시적 오류(`LmsError`)로 보고 세션을 유지한다. 게이트웨이가 Canvas 연결 정보를 주지 않거나 학교 로그인 화면으로 보내는 경우만 SSO 만료로 판단한다.
- 학교 비밀번호 저장을 중단하기 전에 만든 DB 백업에는 암호화된 비밀번호가 남아 있다. 보존 기간이 지나면 폐기한다.

## 11. 개인 액세스 토큰 기반 복구 (2026-11-07)

구현: `app/lms/personal_token.py`, `app/services/lms_access.py`.

개인 토큰은 LearningX Bearer 토큰과 다르다. 실제 계정에서 개인 토큰을 LearningX에 직접 보내면
HTTP 400, Canvas 쿠키만 보내면 HTTP 401이 반환됐다. 다음 정상 연결로 별도의 LearningX 토큰을 얻었다.

1. 개인 토큰으로 Canvas `/api/v1/users/self/profile` 본인 확인.
2. `/login/session_token`의 일회용 주소로 새 Canvas 웹 세션 생성 및 사용자 재확인.
3. 수강 과목의 탭에서 주차학습 메뉴를 탐색하고 Canvas가 만든 서명된 LTI 폼 확인.
4. 폼을 `/learningx/lti/modulebuilder`에 전달해 `xn_api_token` 발급.
5. 별도 쿠키 없는 클라이언트에서 LearningX Bearer 인증으로 학기·과목·출석·모듈 확인.

기존 쿠키와 비밀번호 없는 상태에서 이 흐름을 반복 확인했고, 구현한 함수로도 과목 10개,
출석현황 10개, 표본 과목의 모듈 15개 및 영상 상세정보를 조회했다.
영상 진입 페이지의 서명된 연결 폼도 확인했으나 영상 도구 실행·재생·출석 변경은 수행하지 않았다.
장기 유효성과 실제 서버 측 만료 후 복구는 아직 별도 측정 대상이다.

계정 화면에서 개인 토큰을 선택적으로 등록할 수 있다. 전체 연결 검증 성공 후에만 개인 토큰과
새 세션을 별도로 암호화해 저장한다. 세션 만료 시 개인 토큰으로 복구하고 실패하면 기존 SSO로
복구한다. 명확한 개인 토큰 거절만 만료로 표시하며 네트워크 장애·권한 부족은 토큰 폐기로 간주하지 않는다.
등록·제거·세션 갱신은 버전 조건으로 저장해 오래된 워커가 최신 자격정보를 덮어쓰지 못한다.
개인 토큰 제거는 서비스 내 암호문만 삭제하며 Canvas에서 토큰 자체를 폐기하지 않는다.
