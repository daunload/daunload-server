# 사용 권한 승인과 동기화 축소 설계

작성일: 2026-11-06 · 대상: `app/api`, `app/services`, `app/worker`, `app/db`, `app/web`
시안: `.superpowers/brainstorm/68033-1793947281/content/access-flow.html`

## 1. 목적

서비스를 관리자가 승인한 사용자만 쓰게 한다. 운영자의 말: "관리자에게 권한을 받은 유저만 사용할 수 있도록", "권한을 추가하거나 제거할 수 있어야 한다". 함께 서버 부담을 줄이기 위해 주기 동기화를 크게 줄인다.

## 2. 목표와 비목표

**목표**
- 로그인 후 승인 여부를 확인한다. 승인된 사용자만 서비스를 쓰고, 아니면 권한 요청 화면을 본다.
- 관리자는 운영 현황에서 요청을 보고 승인·거절하며, 승인한 권한을 회수할 수 있다.
- 새 요청이 오면 관리자에게 디스코드로 알린다.
- 승인 전·거절·회수 상태에서는 사용자의 백그라운드 작업을 모두 멈춘다.
- 주기 동기화는 자동 재생 과목만 2시간마다 한다.

**비목표**
- 관리자 계정 자체의 추가·삭제(지금처럼 `ADMIN_STUDENT_IDS` 설정).
- 요청 사유 입력, 승인 만료 기한, 여러 단계 승인.
- 승인 상태 변경의 별도 감사 로그(마지막 결정만 저장한다).

**이렇게 되면 실패다**
- 승인되지 않은 사용자가 API로 데이터를 읽거나 재생·다운로드·동기화를 시작할 수 있다.
- 회수된 사용자의 재생, 동기화, 알림이 계속 돈다.
- 관리자가 자기 자신을 잠가 버릴 수 있다.

## 3. 운영자가 정한 것

- 이미 가입한 사용자도 예외 없이 승인을 받아야 한다. 배포하면 관리자를 뺀 전원이 `요청 안 함` 상태로 시작한다.
- 승인 전·거절·회수 상태에서는 동기화, 자동 재생, 알림을 모두 멈춘다.
- 동기화 A안: 45분 주기 전체 동기화를 없앤다. 승인된 사용자 중 자동 재생을 켠 과목이 있는 사람만, 그 과목을 2시간마다 동기화한다. 나머지 데이터는 로그인할 때와 `LMS 동기화`를 누를 때만 갱신된다. 새 공지·새 과제 알림은 사실상 사라지고, 마감 알림은 마지막 동기화 정보로 계속 간다.
- 새 요청은 관리자에게 디스코드로 알린다.
- 거절 기능이 있다.
- 시안대로 진행한다: 사용자 상태 화면 4가지, 운영 현황 맨 위 요청 표, 사용자 탭의 권한 열·필터·버튼, 요청하지 않은 사용자도 `바로 승인`.

## 4. 설계자 판단 (운영자 확인 없이 정함)

- 관리자(`is_admin`)는 저장된 상태와 관계없이 항상 승인된 것으로 본다. 관리자는 다른 관리자나 자신을 회수·거절할 수 없다(버튼 없음, API 400).
- 디스코드 알림은 관리자 계정이 `알림` 메뉴에 등록한, 사용 중인 디스코드 채널로 보낸다. 없으면 보내지 않는다.
- 거절 후 24시간이 지나야 다시 요청할 수 있다. 회수된 사용자는 바로 다시 요청할 수 있다.
- 회수는 즉시 적용한다. 진행 중이거나 대기 중인 재생 묶음은 중지를 요청한다. 토큰은 그대로 두되 모든 요청에서 상태를 확인한다.
- 승인하면 그 사용자의 전체 동기화를 한 번 큐에 넣어 데이터를 채운다.
- 권한 회수에는 확인 창을 띄운다(진행 중인 재생도 멈춘다는 안내). 승인과 거절은 확인 없이 바로 실행하고 토스트로 알린다.
- 사용자는 대기 중일 때 `상태 다시 확인`으로 새로고침할 수 있다. 자동 갱신은 하지 않는다.

## 5. 데이터

`users`에 컬럼을 더한다. 마이그레이션의 기본값은 `none`이다.

| 컬럼 | 형식 | 설명 |
|---|---|---|
| `access_status` | str(16), 기본 `none` | `none`, `pending`, `approved`, `rejected`, `revoked` |
| `access_requested_at` | datetime, null | 마지막 요청 시각 |
| `access_decided_at` | datetime, null | 마지막 승인·거절·회수 시각 |
| `access_decided_by` | str(32), null | 결정한 관리자 학번 |
| `access_reject_count` | int, 기본 0 | 거절된 횟수 |

`has_access(user) = is_admin(user) or user.access_status == "approved"`를 한 곳에 둔다.

## 6. API

### 사용자
- `GET /me`: 기존 필드에 `access_status`, `access_requested_at`, `access_retry_at`(거절 후 다시 요청할 수 있는 시각, 없으면 null)을 더한다. 관리자는 `approved`로 응답한다.
- `POST /access/request`: `none`, `revoked`, 24시간이 지난 `rejected`에서 `pending`으로 바꾸고 관리자에게 알린다. 이미 `pending`이면 아무것도 바꾸지 않고 200. 승인된 사용자 400. 24시간 전의 `rejected`는 429와 `access_retry_at`.

### 차단
- 다음을 뺀 모든 사용자 API는 `ApprovedUser`(로그인 + `has_access`)를 쓴다: `/auth/*`, `GET /me`, `DELETE /me`, `POST /access/request`, 정적 파일, 개인정보처리방침.
- 막힌 요청은 403과 `detail = {"code": "ACCESS_REQUIRED", ...}`. 화면은 이 응답을 받으면 권한 화면으로 바꾼다.
- 로그인(`POST /auth/login`)은 승인되지 않은 사용자에게 동기화를 큐에 넣지 않는다.

### 관리자
- `GET /admin/access-requests`: `pending` 사용자 목록(학번, 요청 시각, 이전 상태 `none`/`rejected`/`revoked`, 거절 횟수). 요청 시각 오래된 순.
- `POST /admin/users/{student_id}/access`, body `{"action": "approve" | "reject" | "revoke"}`:
  - `approve`: `pending`, `none`, `rejected`, `revoked` → `approved`. 전체 동기화를 큐에 넣는다.
  - `reject`: `pending` → `rejected`, 거절 횟수 +1.
  - `revoke`: `approved` → `revoked`. 활성 재생 묶음의 중지를 요청한다.
  - 그 밖의 전이는 409. 관리자 대상은 400. 결정 시각과 결정자를 저장한다.
- `GET /admin/users`: 각 줄에 `access_status`를 더하고, `access` 필터(`approved`, `pending`, `rejected`, `revoked`, `none`)를 받는다. 관리자 줄은 `approved`.
- `GET /admin/overview`: `pending_count`를 더한다.

이 설계로 어드민은 더 이상 조회 전용이 아니다. 쓰기 API는 위 하나뿐이며 `AdminUser`만 부를 수 있다.

## 7. 백그라운드 작업

- **주기 동기화:** `schedule_syncs`는 `has_access`이고 `auto_play`인 현재 학기 과목이 있는 사용자만 고른다. `next_sync_at` 간격은 120분(지터 유지). 이 동기화는 `auto_play` 과목만 처리한다.
- **부분 동기화:** `sync_user(db, user_id, course_ids=None)`. `course_ids`가 있으면 그 과목의 영상·과제·공지만 갱신하고, 다른 과목의 줄은 비활성화하지 않는다. 학기와 과목 목록 조회는 그대로 한다.
- **전체 동기화:** 로그인, `LMS 동기화` 버튼, 승인 직후. `last_synced_at`은 전체 동기화 때만 바꾼다.
- **자동 재생:** 부분 동기화 뒤 기존처럼 `create_auto_batch`를 부른다. 승인되지 않은 사용자는 만들지 않는다.
- **알림:** `notify_user`가 받는 사람의 `has_access`를 확인하고, 아니면 보내지 않는다. `deadline_reminders`는 승인된 사용자만 고른다.
- **재생 워커:** 묶음을 시작하기 전에 소유자의 `has_access`를 확인하고, 아니면 묶음을 취소로 끝낸다.

## 8. 화면

### 사용자 (시안 1)
- `boot()`는 `/me`를 먼저 읽는다. 승인되지 않았으면 앱 대신 권한 화면을 보여 준다. 상태는 `none`, `pending`, `rejected`, `revoked` 네 가지 문구를 따른다.
- 권한 화면에는 요청 버튼(또는 다시 요청 시각), 상태 다시 확인, 로그아웃, 계정 삭제만 있다.
- 앱을 쓰는 중에 `ACCESS_REQUIRED`를 받으면 권한 화면으로 바꾼다.

### 관리자 (시안 2, 3)
- 운영 현황 맨 위: `pending`이 있으면 `권한 요청 N건` 표(학번, 요청 시각, 이전 상태, 승인·거절). 처리한 줄은 표에서 빠지고 토스트를 띄운다.
- 사용자 탭: 권한 열, 권한 필터, 줄마다 상태에 맞는 버튼(승인, 거절, 권한 회수, 바로 승인). 회수는 확인 창.
- 사용자 상세 머리말에도 권한 상태와 같은 버튼을 둔다.

## 9. 개인정보와 문서

- `privacy.html`: 권한 요청·결정 기록(요청 시각, 결정 시각, 결정자, 거절 횟수)을 처리하고, 승인 전에는 학교 정보를 동기화하지 않는다는 점, 주기 동기화를 자동 재생 과목으로 줄였다는 점을 적고 시행일을 고친다.
- 개인정보 안내(`#privacy-notice`)의 저장 키를 바꿔 한 번 더 보여 준다.
- README와 `design-system/MASTER.md`의 어드민 절에 승인 흐름과 쓰기 동작을 적는다.

## 10. 배포

- 배포 직후 관리자를 뺀 모든 사용자가 막힌다. 운영자는 배포 직후 사용자 탭의 `요청 안 함` 필터에서 계속 쓸 사람을 `바로 승인`할 수 있다.
- 마이그레이션은 컬럼 추가만 한다. 되돌리기는 컬럼을 지운다.

## 11. 테스트

- API: 막힌 경로 403과 열린 경로 200, 상태 전이 표 전체(허용·409·400·429), 관리자 예외, 디스코드 알림 대상과 실패 무시, 회수 시 재생 중지, 승인 시 동기화 큐.
- 백그라운드: 주기 동기화 대상 선별, 부분 동기화가 다른 과목을 비활성화하지 않음, 승인 안 된 사용자의 알림·자동 재생·재생 시작 차단.
- 화면: 상태 4가지, 요청 보내기, `ACCESS_REQUIRED` 전환, 관리자 요청 표·버튼·필터·확인 창, 375·1440px 가로 스크롤 없음.
- Postgres: 새 컬럼과 필터가 들어간 어드민 쿼리.

## 12. 구현 전 검토에서 정한 것 (설계자 판단)

- **서명 링크도 막는다.** `/downloads/{token}`, `/audio/{token}`처럼 로그인 대신 서명된 토큰으로 여는 경로와 다운로드 완료 보고도 토큰 주인의 `has_access`를 확인한다. 회수된 사용자가 이미 받은 링크로 내려받을 수 없어야 한다.
- **로그인은 열어 둔다.** 승인 전에도 학교 계정 확인과 자격 증명 저장은 지금처럼 한다(승인 직후 동기화에 필요). 동기화만 큐에 넣지 않는다.
- **동기화 작업을 둘로 나눈다.** 전체 동기화는 지금의 `sync_user_job`과 작업 ID `sync:{uid}`, 자동 재생 과목 동기화는 별도 작업 함수와 작업 ID `autosync:{uid}`를 쓴다. 승인·로그인·버튼의 전체 동기화가 부분 동기화 때문에 버려지지 않게 한다.
- **부분 동기화 범위:** 고른 과목의 과목 정보, 영상·과제·퀴즈 할 일, 과제 목록, 공지, 저장 영상 주소만 갱신한다. 고르지 않은 과목의 줄은 그대로 두고 비활성화하지 않는다. 새 공지 알림과 마감 알림은 그 과목에 대해서만 기존 규칙대로 보낸다.
- **디스코드 알림:** 상태가 `pending`으로 바뀔 때만, 모든 관리자의 사용 중인 디스코드 채널로 한 번씩 보낸다. 이미 대기 중인 요청을 다시 눌러도 알리지 않는다. 같은 사람이 회수 후 다시 요청하면 다시 알린다. 전송 실패는 기록만 하고 요청은 성공시킨다.
- **회수 시 재생 중지:** 대기·진행 중인 묶음에 `cancel_requested`를 세운다. 워커는 묶음을 시작하기 전에 `has_access`를 확인한다. 영상 하나마다 다시 확인하지는 않는다.
- **테스트 사용자:** 기존 API 테스트의 일반 사용자는 승인된 상태로 시작하게 하고, 승인 전 상황은 테스트에서 명시적으로 만든다.
- **다시 요청 시각:** 거절 결정 시각(`access_decided_at`)부터 24시간. 승인하면 `access_retry_at`은 없어지고, 거절 횟수는 기록이므로 유지한다.
- **시안 위치:** 저장소에 들어가지 않는 폴더라, 구현 작업 공간에 복사해 전달한다.

## 13. 구현자에게 맡기는 것

엔드포인트 내부 구조, 상태 전이 함수 위치, 부분 동기화의 코드 분리 방식, 문구의 세부 표현(시안의 뜻을 유지), 디스코드 메시지 형식.
